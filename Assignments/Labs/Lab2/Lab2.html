Lab Overview

In Lab 1, you built and evaluated an LLM-powered chatbot and then extended that application with web search. This lab builds directly on that work, but shifts the central question from what can an LLM application answer? to what does it mean for an application to act as an agent?

You will begin with the concepts from Chapter 2 and our discussion of the five-level agent taxonomy. You will then transform a simple LLM application into a small, goal-directed system that can select actions, observe the results, and decide what to do next.

The implementation will use a simplified ReAct loop:

THOUGHT → ACTION → OBSERVATION → THOUGHT → ACTION → … → FINAL ANSWER

The goal is not to build a production agent. The goal is to understand the smallest set of components required to create agent-like behavior and to recognize the engineering tradeoffs introduced by autonomy.

Learning Objectives

Upon successful completion of this lab, students will be able to:

  • Distinguish scripted automation, an LLM application, and an agent using the five-level taxonomy discussed in lecture.
  • Describe an agent using concepts from Chapter 2, including goals, percepts, actions, environments, and performance measures.
  • Explain the purpose of the ReAct Thought → Action → Observation loop.
  • Extend an existing LLM application with a small set of callable tools.
  • Implement a bounded agent loop that can use observations to determine subsequent actions.
  • Instrument an agent so that its actions and observations can be inspected.
  • Identify common failure modes involving tool selection, missing information, repeated actions, and step limits.
  • Defend the level of agency represented by your implementation.

Part 1 — From Automation to Agency

Before writing code, classify the following systems using the five-level taxonomy from lecture. The purpose of this exercise is to establish what changes as we move from predetermined automation toward autonomous behavior.

LevelDescriptionKey Characteristic
Level 0 — Scripted AutomationExplicit rules determine what the system does.The developer determines the sequence of actions.
Level 1 — LLM as a ComponentAn LLM generates or transforms information within an application.The surrounding application still determines the workflow.
Level 2 — Tool-Using LLMThe LLM can select from available tools.The model can choose an action rather than only generate text.
Level 3 — Goal-Directed AgentThe system can pursue a goal through multiple actions.Later actions can depend on observations from earlier actions.
Level 4 — Persistent AgentThe system maintains information across interactions.Persistent state or memory influences future behavior.
Level 5 — Multi-Agent SystemMultiple agents interact to accomplish tasks.Agency is distributed across multiple cooperating or competing agents.

You may reuse your Lab 1 Tavily implementation. The important change is who decides when the search occurs. In Lab 1, your application searched first and then passed the results to the LLM. In this lab, the LLM should be able to decide whether a search is necessary.

📖 Reference Documentation Python — eval() for the Calculator Tool
eval() — Python Standard Library ↗
eval() will evaluate an arithmetic expression string, but by default it can reach Python's entire built-in namespace. When the string being evaluated comes from model-generated input, that is a real code-execution risk, not a hypothetical one. Restrict what eval() can see by supplying explicit globals/locals dictionaries, e.g. eval(expression, {"__builtins__": {}}, allowed_names), where allowed_names contains only the arithmetic functions you intend to expose.
  • ast.literal_eval() — Python Standard Library ↗ — a safer alternative worth knowing about when you only need to parse literal values (numbers, strings, lists) rather than evaluate expressions.

Tool-Using Flow

USER QUESTION → MODEL → TOOL SELECTION → TOOL RESULT → MODEL → FINAL ANSWER

"Search the web."

Explain why the second description gives the model more useful information about when and how to use the tool.

📖 Reference Documentation OpenRouter — Tool / Function Calling
Client Tools — OpenRouter Documentation ↗
OpenRouter uses the OpenAI-compatible tools request parameter. Each tool is described with a name, a natural-language description, and a JSON Schema parameters object listing the arguments the model may supply. The model never executes a tool itself — it returns a tool_calls array naming the requested tool and its arguments as a JSON string, your program executes the corresponding Python function, and the result is appended back into messages with role: "tool" (matched to the request via tool_call_id) so the model can observe it on the next turn. This request/execute/observe cycle is what makes the ReAct loop possible.

Part 5 — Observe Your Agent

Once your implementation works, modify the console output so that you can see what the agent is doing at each step. You are not being graded on producing a hidden chain-of-thought transcript. The purpose is to make the agent loop observable.

Your output should make it possible to identify:

  • The current step number.
  • Which tool the model selected.
  • The arguments supplied to that tool.
  • The observation returned by the tool.
  • When the agent stops and produces its final answer.

Example Trace

--- STEP 1 --- ACTION: search_web ARGUMENTS: {"query": "Montana population 2025"} OBSERVATION: ... --- STEP 2 --- ACTION: calculator ARGUMENTS: {"expression": "1,140,000 * 2"} OBSERVATION: 2,280,000 --- STEP 3 --- FINAL ANSWER: Approximately 2.28 million.
📖 Reference Documentation The content Property on Reasoning Models
Reasoning Tokens — OpenRouter Documentation ↗
A returned message has two fields worth distinguishing when you log the THOUGHT step. message["content"] is the model's ordinary text output — on a turn where the model only requests a tool call, many models leave this field empty or null. Reasoning models can additionally return a separate message["reasoning"] field containing their internal reasoning trace, which some providers omit unless the request asks for it. Your THOUGHT logging should handle both cases gracefully rather than assuming content is always populated.
