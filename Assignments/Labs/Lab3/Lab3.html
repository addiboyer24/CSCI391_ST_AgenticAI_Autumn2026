Learning Objectives

Upon successful completion of this lab, students will be able to:

  • Identify context saturation ("Lost in the Middle") and implement windowed summarization to bound context growth.
  • Identify instruction drift and implement persistent constraint reinjection to keep critical rules from decaying.
  • Reduce confident confabulation by enforcing structured output schemas on tool call arguments, both online (OpenRouter) and offline (local llama.cpp).
  • Design tools that fail loudly and explicitly rather than silently returning ambiguous empty results.
  • Instrument an agent with structured, per-tool-call observability logging.
  • Write tool schemas — names, descriptions, and optional parameters — that a junior engineer (or a small model) could follow correctly on the first try.
  • Detect drift between a pinned model configuration and the model actually in use at runtime.
  • Measure and compare latency, token cost, and run-to-run accuracy variance for the same agent and the same prompt.

Part 0 — Environment Setup & Validation

This lab introduces two concepts you have not used in Labs 1 or 2. Read both before touching any code.

New Concept: Online vs. Offline Mode

So far, every lab has talked to exactly one place: OpenRouter. Starting in this lab, your agent can run in either of two modes against the identical OpenAI-compatible request format:

ModeWhat It Talks To
onlineOpenRouter, exactly as in Labs 1 and 2.
offlineA local model server (llama.cpp) running on your own machine at http://127.0.0.1:8080, serving open-weight models you download yourself.

Because both expose the same /v1/chat/completions endpoint shape, your agent code can accept a mode argument and reuse identical request-building logic for either one.

New Concept: Model Tiering

Instead of one model string doing every job, this lab configures two per mode: a cheap model that drives the mechanical, repetitive parts of the ReAct loop (tool selection), and an expensive model that is invoked once, only to synthesize final_answer. This is the tiered-reasoning pattern from your Chapter 5 reading, applied to agent tool-calling rather than classification.

Step 1 — Install llama.cpp

If you plan to run offline, you need the llama.cpp tools (llama-server / llama serve) installed on your own machine.

Windows (PowerShell):

winget install llama.cpp

Mac (Terminal):

brew install llama.cpp

Step 2 — Confirm the Installation With a Single Model

Before configuring tiering, prove llama.cpp itself is installed and can serve a model. Start a server with one model directly by its Hugging Face repo id:

Part 3 — The Agent: Multi-Ticker Momentum Research Agent

For this lab, every student implements the same agent so that failure-mode behavior is comparable across the class. You will build a research agent that compares several stock tickers and reports which one shows the strongest short-term momentum.

ℹ Why This Task A single-ticker lookup finishes in 2–3 steps — too short to observe context saturation or instruction drift. A four-ticker comparison, where each ticker requires a structured data lookup and a news search, naturally produces 10–15 ReAct steps on a correct run — long enough to make every failure mode in Part 1 observable, and short enough to stay debuggable. Set MAX_STEPS = 15.

Required Tools

get_stock_snapshot(ticker)Returns simulated price, day-change percentage, and volume for a fixed set of tickers. Not real market data — a deterministic fixture so that results are comparable across runs and students.
search_web(query)Your Lab 1/2 Tavily-backed search tool, reused as-is.
calculator(expression)Your Lab 2 sandboxed calculator tool, reused as-is.
final_answer(...)Terminal tool. Its arguments are schema-constrained — see Part 4.
ℹ Design Principle: final_answer Is a Tool Call, Not an Absence of One In Lab 2, the loop ended whenever the model stopped requesting a tool — its plain-text reply was the final answer. This lab uses the pattern recommended by Caldwell in The Agentic AI Bible: the final answer is itself a schema-constrained tool call, exactly like every other action in the loop, rather than something inferred from silence. Concretely: a model choosing not to call a tool is only ever a signal to move toward finalizing — it is never treated as the answer itself. The actual answer is only accepted once final_answer is explicitly invoked with arguments that pass its schema. This keeps termination machine-checkable (you know the agent is done because a specific named event happened, not because nothing else happened) and keeps the answer itself subject to the same structured-output enforcement as any other tool argument — closing the one gap where a "plain text" response could otherwise slip past every mitigation in Part 6.

Required Test Prompt

Compare NVDA, AMD, INTC, and QCOM. For each one, get its current stock snapshot and find one recent news headline. Then tell me which one shows the strongest momentum right now, and why.

This is the prompt you will use for every experiment and benchmark in this lab unless a section says otherwise, so that your results are directly comparable across sections.

Part 4 — Tool Schema Discipline

Inconsistent schema adherence is rarely a model failure. It is usually a specification failure: an ambiguous name, a vague description, or an "optional" parameter the model can't tell whether it's supposed to fill in.

Write Descriptions for a Junior Engineer

Compare these two descriptions for the same tool:

"Gets stock info."

versus:

"Returns a structured price snapshot for one publicly traded ticker symbol from a fixed lookup table. Use this whenever the user asks about a specific ticker's current price, day change, or volume. Do not use this for company news or qualitative information — use search_web for that instead. If the ticker is not in the lookup table, this tool returns an explicit error object rather than a price."

The second description does three things the first does not: it says when to use the tool, it says when not to (disambiguating it from search_web), and it tells the model what to expect on failure.

Rules for Every Tool You Ship in This Lab

  1. Distinctive names. No two tools should have names a skimming reader could confuse (get_data and fetch_data is a failure; get_stock_snapshot and search_web is not).
  2. Truly optional parameters. If a parameter is marked optional in the JSON Schema, the tool must behave sensibly when it is omitted. Do not mark a parameter optional because you don't want to think about validating it.
  3. Say when not to use the tool whenever a plausible mix-up exists with another tool in the same toolset.
  4. Document the failure shape. The description should tell the model what an error response looks like, not just what success looks like.

Part 5 — Explicit Error Signals

A tool that silently returns an empty result on invalid input is training the model to guess. Compare these two implementations of a lookup tool:

def get_stock_snapshot_BAD(ticker): # Silent failure: an unknown ticker looks identical to # "this stock currently has no data," which invites the model # to fill the gap with a plausible-sounding guess. return MOCK_MARKET_DATA.get(ticker.upper(), {}) def get_stock_snapshot_GOOD(ticker): key = ticker.upper().strip() if key not in MOCK_MARKET_DATA: # Explicit, structured, unambiguous. The model cannot mistake # this for a valid (if boring) snapshot. return { "error": "TICKER_NOT_FOUND", "message": f"'{key}' is not in the simulated market data set.", "valid_tickers": sorted(MOCK_MARKET_DATA.keys()), } return MOCK_MARKET_DATA[key]

Part 6 — Structured Outputs Against Confabulation

A tool's parameters object is already a JSON Schema. Whether that schema is actually enforced — versus treated as a suggestion the model can ignore — depends on which backend you're calling and how you configure the request. This is the single most direct lever you have against confident confabulation: a model cannot invent a field that a grammar-constrained decoder will not let it emit.

PathOnline — OpenRouterOffline — Local llama.cpp
MechanismProvider-dependent. For providers that implement it, response_format: {"type": "json_schema", ...} is enforced at the provider's decoding layer.Your schema is converted to a GBNF grammar and handed to the sampler — invalid tokens are simply disallowed, not merely discouraged.
Enabling itSet response_format.type = "json_schema" with strict: true. For tool calls specifically, the same tools[].function.parameters schema applies.Requires --jinja so the model's own chat template (including its tool-call format) is rendered rather than a generic fallback.

Part 7 — Observability: Log Every Tool Call

Console printing (Lab 2) is enough to watch one run. It is not enough to compare five runs, debug a failure that happened yesterday, or feed a benchmark script. Every tool call and every tool result must also be written to a structured, append-only log.

Minimum Log Record

timestampISO-8601 timestamp of the tool call.
stepThe ReAct step number this call occurred on.
tool_nameWhich tool was invoked.
argumentsThe exact arguments the model supplied.
resultWhat the tool returned — including error objects.
latency_msWall-clock time the tool call took to execute.

What Is a JSONL File?

A .jsonl ("JSON Lines") file is plain text where each line is one complete, independent JSON value — not one big JSON array spanning the whole file. That distinction is exactly why it's the right format for an append-only log: adding a new record means opening the file in append mode and writing one more line, with no need to read, parse, and rewrite everything that came before.

{"step": 1, "tool_name": "get_stock_snapshot", "arguments": {"ticker": "NVDA"}, "result": {"ticker": "NVDA", "price": 187.42}, "latency_ms": 142.3} {"step": 1, "tool_name": "search_web", "arguments": {"query": "NVDA news"}, "result": "...", "latency_ms": 890.1} {"step": 2, "tool_name": "get_stock_snapshot", "arguments": {"ticker": "AMD"}, "result": {"ticker": "AMD", "price": 152.08}, "latency_ms": 138.7}
import json # Write one record -- each call appends exactly one line: with open("agent_trace.jsonl", "a") as f: f.write(json.dumps(record) + "\n") # Read every record back, oldest first: with open("agent_trace.jsonl") as f: records = [json.loads(line) for line in f if line.strip()]
⚠ A Common Gotcha json.dumps() cannot serialize a Python datetime object directly — it raises TypeError: Object of type datetime is not JSON serializable. Convert timestamps to strings first with datetime.now(timezone.utc).isoformat() before building your record, rather than storing the raw datetime object in it.

Part 8 — Context Saturation & Windowed Summarization

Liu et al. (2023/2024) showed that language models exhibit a U-shaped performance curve over long inputs: information at the very beginning or very end of the context is used reliably, while information buried in the middle is frequently ignored — regardless of whether the model's context window is technically large enough to hold it.

📖 Reference Documentation Liu, Lin, Hewitt, Paranjape, Bevilacqua, Petroni & Liang (2024)
"Lost in the Middle: How Language Models Use Long Contexts." Transactions of the Association for Computational Linguistics, 12:157–173.
arXiv:2307.03172 ↗  |  ACL Anthology ↗

An unbounded ReAct transcript — every tool call and every tool result appended forever — is exactly the shape this paper warns about: by step 12 of a 15-step task, the observation from step 2 is buried in the middle of a growing transcript, competing with everything since for the model's attention.

The Windowing Rule

Instead of appending every tool call/result pair verbatim forever, keep only the most recent WINDOW_SIZE steps in full. Anything older is folded into a single rolling summary message that sits where those steps used to be.

STEP 1 … STEP (n − x)  →  ROLLING SUMMARY
STEP (n − x + 1) … STEP n  →  KEPT VERBATIM
↓
Both are sent to the model together — a short, fresh summary plus a small, recent, fully-detailed tail.
WINDOW_SIZE = 4 # steps kept verbatim; tune during Experiment A def build_windowed_context(all_steps, rolling_summary): # all_steps: the full list of {role, content, ...} messages generated # so far, grouped by ReAct step. # TODO 3: If len(all_steps) <= WINDOW_SIZE, no windowing is needed yet. # Return all_steps unchanged. # TODO 4: Otherwise, split into steps_to_summarize and steps_to_keep, # where steps_to_keep is the last WINDOW_SIZE steps. # TODO 5: Fold steps_to_summarize into rolling_summary. You may do this # with a cheap-tier model call ("summarize these tool results in 2-3 # sentences, preserving concrete numbers and ticker symbols exactly") # or with a deterministic Python summarizer that extracts key fields # (ticker, price, headline) without calling the model at all. # TODO 6: Return [system_prompt, rolling_summary_message] + steps_to_keep. pass
⚠ Preserve Concrete Values A summary that says "gathered data on several tickers" has destroyed the exact numbers your final_answer needs. Your summarizer must preserve specific ticker symbols, prices, and percentages verbatim — summarize the narrative, not the data.

Part 9 — Instruction Drift & Persistent Reinjection

A system prompt is not a contract the model consults on every turn — it is one message among many, and its relative influence shrinks as the conversation grows around it. Treating the system prompt as write-once is the anti-pattern; treating your most critical constraints as repeating obligations is the fix.

The Reinjection Pattern

Identify the 2–3 rules whose violation would most damage the final answer (you already named the highest-stakes one in Part 2). Re-send a short reminder message containing exactly those rules on every step — not the whole system prompt, just the load-bearing constraints — placed at the end of the message list, immediately before the model's turn.

Part 10 — Model Tiering & Version Drift Detection

"Use the biggest model for every step in the loop" is an easy default and a real cost/latency liability: most steps in your ReAct loop are mechanical tool selection, and only final_answer synthesis benefits meaningfully from a stronger model. Apply the tiered pattern you set up and validated in Part 0: a cheap model drives the loop, an expensive model is reserved for synthesis.

The Drift Check

A pinned model string in .env is only useful if it's actually what's running. Add a startup check that compares the model your agent is about to call against what .env says it should be — catching the case where a teammate (or you, at 1 a.m.) hardcoded an override that was never written back to .env.

Part 12 — Benchmark: Latency, Cost, and Accuracy

A single successful run tells you the agent can work. Repeated runs of the identical prompt tell you how reliably it works — and whether your mitigations from Parts 6–10 actually reduce variance, not just look reasonable on paper.
