Lab Overview

As an agent gains tools, every call carries every tool definition, and the model has more ways to pick the wrong one. A common fix is a routing step: before the main agent runs, a cheap model reads the request and decides which group of tools it needs. The agent then sees only that group.

In this lab you will build that routing step as a meta tool called get_available_tools(). It does no work on the user's behalf; it only decides which tools the real work will need. It is not connected to an agent loop yet.

USER PROMPT
↓
get_available_tools()  (cheap model)
↓
{"domains": [...], "tools": [...]}

Learning Objectives

Upon successful completion of this lab, students will be able to:

  • Explain why tool routing reduces cost and tool-selection errors.
  • Constrain model output with a JSON Schema enum instead of free-form text.
  • Force a structured classification with tool_choice.
  • Validate model output in code and fall back safely when it is invalid.

Part 2 — Enums, Not Descriptions

Complete CLASSIFIER_SCHEMA by adding one required property, domains: an array of strings restricted by a JSON Schema enum. An array is needed because one prompt can touch several domains.

How enum Works

The enum keyword restricts a value to a fixed list. A value is valid only if it exactly equals one of the listed elements — case, spelling, and type all count. The list should have at least one element, and its elements should be unique. enum can stand alone or sit beside type; for an array of choices, put it on items so it applies to every element:

"domains": { "type": "array", "items": {"type": "string", "enum": ["calendar", "email", "files", "billing", "none"]}, "description": "Every toolset domain the request needs." }
Value of domainsValid?
["email", "billing"]Yes
["Email"]No — case differs
["weather"]No — not in the list
"email"No — a string, not an array
⚠ Not Acceptable — valid values only in the description "items": {"type": "string"}, "description": "Valid values are calendar, email, files, billing, or none."
ℹ Why It Matters A description is a hint the model may ignore. An enum is part of the schema: backends that enforce schemas can constrain output to it, and your code can check against it. The final_answer.confidence field in the Chapter 3 coffee agent uses the unacceptable pattern — nothing stops the model from returning "pretty sure."

Validating JSON Against a Schema

The same JSON Schema you send the model can also check what comes back. The jsonschema library does this with one function:

  • jsonschema.validate(instance, schema) returns None if the already-decoded data satisfies the schema; otherwise it raises jsonschema.ValidationError, whose .message says why.
  • jsonschema.SchemaError means the schema itself is malformed — a bug in your code, not the model's.
  • json.loads() raises json.JSONDecodeError before validation ever runs if the model's string isn't JSON at all.

Example. This validates t-shirt orders, not routing results — applying the pattern to classify_intent is your job.

import jsonschema ORDER_SCHEMA = { "type": "object", "properties": { "sizes": {"type": "array", "items": {"type": "string", "enum": ["S", "M", "L"]}}, }, "required": ["sizes"], } for order in [{"sizes": ["S", "L"]}, {"sizes": ["XL"]}, {"sizes": "M"}, {}]: try: jsonschema.validate(instance=order, schema=ORDER_SCHEMA) print(order, "valid") except jsonschema.ValidationError as err: print(order, "invalid:", err.message)
{'sizes': ['S', 'L']} valid {'sizes': ['XL']} invalid: 'XL' is not one of ['S', 'M', 'L'] {'sizes': 'M'} invalid: 'M' is not of type 'array' {} invalid: 'sizes' is a required property
💡 Try This Add {"sizes": []} to the list. Does it pass? Decide whether an empty domains list should be caught by your schema or by your own code — the JSON Schema array reference in Part 2 has a keyword for it.

C. Final Lab Reflection

Answer the following questions. Keep each response to 2–4 sentences unless otherwise indicated.

1. Why is an enum more reliable than listing the valid values in a description?

2. If the router returned a domain your code didn't expect, what would break downstream? How does your validation prevent it?

3. Why is the fallback "every toolset" rather than "no tools"?

4. In one sentence, why is a cheap model a good fit for routing?

Final Thought The router never does the user's work — it only narrows the choices. Constraining a model's output to a fixed set of values is one of the simplest, highest-leverage reliability tools you have, and you will use it again every time an agent has to pick from a menu.
