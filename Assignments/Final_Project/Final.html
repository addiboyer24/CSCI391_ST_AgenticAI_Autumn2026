Project Overview

Part 2 — Planning (choose one)

All options share three requirements: the plan or reflection is logged as its own trace event, it is legible to your code (not only to the model), and it is bounded (step budgets, retry counts, branch counts).

Option 2A — Plan-and-Execute

Best for: multi-part requests with a known structure where a wrong step wastes several later ones.
  • Representation: a numbered markdown plan with status markers [ ], [x], [!]. Each step names the tool, the rough input, and a completion criterion. "Find good songs" is a sub-goal, not a step.
  • Parser: your code parses the plan, finds the first incomplete step, enforces a per-step budget, and reinjects the updated plan each iteration.
  • Plan validation (optional): a code or cheap-model check that rejects plans that are too coarse, too fine, or missing a dependency (for example, a write before verify_recordings).
  • Plan revision: when a step fails or reveals something unexpected, a revision call rewrites the remaining steps. Demonstrate one revision that prevents plan fixity.
  • Stall detection: a step attempted three times without completing is marked [!] and triggers revision or escalation.

Option 2B — Reflexion (production form)

Best for: requests where failures are frequent but recoverable, such as MBID lookups, schema validation, and empty search results.
  • Failure detection fires on (a) a tool input or resource error, (b) a claim that a later tool result contradicts, and (c) a structured output that fails Pydantic or jsonschema validation.
  • Reflection call: cheap model, separate system prompt, given the failed step, its trace, and the error. Its output is a [REFLECTION]-tagged message saying what went wrong and what to try instead.
  • Reflections accumulate, so the third attempt sees two prior reflections. The retry count is bounded (at most 3). If two attempts produce the same output, log a reflection_ignored event.
  • Promotion (optional): promote one reflection that reveals a systemic error into prompts/system_v2.md or a tool description, with a changelog entry, and show the next session avoiding the mistake.

Option 2C — Tree-of-Thoughts

Best for: high-branching choices where a wrong early commitment is expensive and you can score candidates cheaply.
  • Find a step in Encore with a real branching factor. Example: choosing among three candidate playlist orderings, seed artists, or lb_radio prompts.
  • Generate N candidates (N ≤ 4), score each, expand the best, with depth ≤ 3. Log the tree.
  • Scorer: deterministic code. Examples: total duration within ±3 minutes of the target, no plays in the excluded window, no artist more than twice, an energy arc (from features you can compute), and every MBID verified. Stop early when a candidate passes every check.
  • Report the cost multiplier (N × scoring calls × depth) against a single-path baseline, and argue it was worth it.

Option 2D — Hybrid (Plan-and-Execute + ReAct + Reflexion) — up to +5 Extra Credit

Best for: long, multi-goal requests. The hardest option, and the pattern most production agents actually use.
  • Outer Plan-and-Execute (all of 2A), an inner ReAct sub-loop per step with its own iteration budget, and a Reflexion call when a sub-loop exhausts its budget or hits a fatal error.
  • The reflection either replaces the failed step (plan revision) or gives a new execution path for the same step (within-step retry). If both fail, the step is marked [!] and handled by a post-plan audit pass.
  • Extra credit: a complete Hybrid earns full Part 2 credit plus up to +5. To earn the +5, your traces must show all three layers working: (1) a ReAct sub-loop exhausting its step budget and triggering a reflection, (2) one plan revision and one within-step retry, each coming from a reflection, and (3) a [!] step picked up by the post-plan audit pass. A Hybrid missing any of these is graded as Plan-and-Execute (2A).
  • The Central Rule still applies: choose it because your traces show both plan drift and frequent recoverable failures, not for the bonus alone.

Part 3 — MCP: A New Feature from a Public Server

Encore becomes an MCP client. You will connect it to a public, third-party MCP server that you did not write, discover the server's tools at runtime, and use them to ship one new feature. This is the case Chapter 9 calls the exception to "don't add MCP to in-process tools": using a community-maintained server instead of writing the integration yourself.

3.1 Choosing a Server

  • Public and free: open source, from the official MCP Registry or a reputable directory, usable without paying. A free API key (for example setlist.fm or Ticketmaster) is fine. Never commit it.
  • Treat it like a third-party npm package with network access. Read its source before you run it, pin an exact version or commit, and write a short review in the README: what it can touch (filesystem, network, credentials) and what you restricted.
  • Read tools first. If the server exposes writes, your approval gate must cover them exactly as it covers create_playlist.
  • Servers that only duplicate an existing Encore tool (for example, a MusicBrainz server used only for search) do not count as a new feature on their own. See Idea 5 in Appendix A for the one way to make that work.

Part 4 — Single-Agent Structure (choose one)

The pattern lives in code, not only in the prompt. Add a --disable <pattern> flag so the ablation in Part 8 can turn it off.

Option 4A — Validator-as-Wrapper

Diagnostic: does Encore's output have to satisfy a hard constraint that can be stated precisely?
  • One second model call checks the draft final_answer against one to three specific, verifiable rules drawn from failures you have seen. Examples: every track named in the answer is in sources; no claim about a playlist that was not created this session; no tour date stated without an MCP source. "Be helpful" is not a rule.
  • Verdict schema: pass | revise (with reason) | block.
  • Fail open: if the validator itself errors, the unvalidated answer is returned and a validator_error metric is logged.
  • At most two revisions, each with "Your previous response was flagged because [reason]." After that, return answered_low_confidence or escalate; never a third unchecked attempt.
  • Give the validator its own prompt (a different model is optional). Report how many happy-path answers it wrongly flagged (false positives).

Option 4B — Stateful Step Machine

Diagnostic: is there a known step order where skipping ahead is a bug and partial completion is meaningful?
  • Encode one Encore workflow as explicit states in code. Example: gather constraints → retrieve candidates → verify → user approves draft → create → export.
  • Code, not the model, decides when a step is complete and when to advance. Completion checks test whether the required information is available, not whether the agent asked the question, so a user who gives everything up front skips cleanly.
  • Each state exposes only its own tools (for example, create_playlist does not exist before verify completes).
  • An explicit, tested escalation path for a step that cannot complete within its retry count. A step machine that loops forever is worse than the flat agent it replaced.

Option 4C — Scratchpad with Explicit Plan

Diagnostic: do Encore's requests routinely run past 6–7 tool calls and drift? (Not allowed with Plan-and-Execute or Hybrid.)
  • A managed scratchpad the model updates at the start of every step, injected by your code at a fixed position in each request.
  • Capped at a word limit you choose and justify. The model prunes completed items, and your code enforces the cap.
  • Show the scratchpad surviving working-memory compression from the midterm (it must never be summarized away).

Part 6 — Human Oversight (Extra Credit, up to +15)

This part is optional. Encore already has a human in the loop: the midterm approval gate on writes, which still counts toward the required grade. Each option below is worth up to +5. Do any combination, for up to +15. Extra credit is awarded only for working, demonstrated features with trace evidence.

Before you start, answer the three risk questions in the workbook: How reversible is the action? How often does Encore operate outside its reliable range? How expensive is the latency of a human review? Place intervention points by the risk of the action, not by how hard the task is. Every option builds on code you already have.

Required for any Part 6 credit, the audit log: for any action taken on human input, your traces answer "who approved this, and when." Log a review_request event and a review_decision event carrying run_id, the decision, the reviewer, and a timestamp.

Option 6A — HITL with Confidence-Gated Escalation (+5)

Best for: a decision Encore sometimes gets confidently wrong, such as fuzzy matches, inferred preferences, or constraints only partly met.
  • Give one decision a measurable confidence score: a match score, the fraction of constraints satisfied, or a validator verdict. The model's self-report alone does not count.
  • Proceed above the threshold and escalate below it. Approval for irreversible writes (export_playlist, delete_playlist) stays on regardless of confidence.
  • Minimal review card: a plain-language summary of the proposed action, the reasoning behind it, and three choices: approve, modify, reject. Modify must work (for example, editing the title or dropping tracks), and the modified action is what runs. Never show the reviewer a raw trace.
  • Calibrate: start with a high threshold. Report the override rate (modify plus reject) per confidence band on your feature set, and propose a new threshold. Bands with overrides below 5% are candidates for less review.

Option 6B — HOTL with a Review Queue (+5)

Best for: a reversible, repetitive action where pausing for every decision would be the bottleneck.
  • Choose one reversible action, such as adding tracks to an [Encore] draft playlist, tagging listens with moods, or enriching artists in a swarm. Encore proceeds without pausing.
  • Low-confidence decisions go to a review queue (a SQLite or JSON table). python encore.py review lists each one as a review card (a plain-language summary and the reasoning) and accepts approve, modify, or reject.
  • Corrections are applied (undo or modify the action) and fed back as a stored preference or a procedural rule. Show one correction changing behaviour in a later session.
  • Irreversible actions still go through the midterm approval gate. Report how many decisions were queued and how many were corrected.

Option 6C — Asynchronous Review with Webhooks (+5)

Best for: long-running work where the reviewer is not watching the terminal. Builds directly on your Part 5 checkpoints.
  • At an intervention point, Encore serializes the review request, saves run state to the Part 5 checkpoint store, posts the request to a review queue, and suspends. The process may exit.
  • A small webhook receiver on localhost (FastAPI or Flask): POST /review/{run_id} with approve, modify, or reject loads the stored state, injects the decision, and resumes the run where it stopped.
  • Demo: start a request, let the process exit, submit the decision later with curl, and show the run finishing. Posting the same decision twice must not run the action twice (idempotent by run_id).
  • Reviews pending longer than a TTL you choose expire, and the run ends with status stuck and a clear message.

Part 8 — Evaluation

  1. Regression. Rerun your midterm 30-request set. Accuracy may not drop by more than 2 requests without an explanation. If it does, that is a finding, not a failure.
  2. Feature set. 10 new requests for your MCP feature (4 happy path, 3 boundary, 3 failure, including server down and the injection fixture), with correct outcomes defined before you run them. Your three golden requests count toward the 10.
  3. Ablations. For each of your three patterns, run a targeted subset of at least 5 requests with the pattern on and with it off (--disable). Report correctness, cost, latency, and tool calls. This is the evidence for the Central Rule. For the multi-agent pattern, "off" means your best single-agent configuration; if the single agent wins, say so. That is a legitimate result.
  4. Fault injection. One run with mcp_crash_after, plus one multi-agent run killed mid-stage and resumed with --resume.
  5. Human oversight (Part 6 extra credit only). On the feature set, report how many decisions were escalated or queued for review and the override rate (modify plus reject). 6A: break this down by confidence band. 6C: include one run resumed by webhook after the process exited.
